    1. `delete_message(conn: &Connection, id: &str) -> Result<()>` — Executes `DELETE FROM messages WHERE id = ?1`. No conversation metadata update needed (used for regenerate which immediately re-adds a message).

    2. `delete_messages_after_sort_order(conn: &Connection, conversation_id: &str, sort_order: i32) -> Result<()>` — Executes `DELETE FROM messages WHERE conversation_id = ?1 AND sort_order > ?2`. This is the truncation operation for edit/resend per D-08. After deletion, also update the conversation's `last_message_preview` to the message at `sort_order` (or the latest remaining message) by querying `SELECT content FROM messages WHERE conversation_id = ?1 ORDER BY sort_order DESC LIMIT 1` and updating the conversation row.

    3. `update_message_content(conn: &Connection, id: &str, content: &str) -> Result<()>` — Executes `UPDATE messages SET content = ?1 WHERE id = ?2`. Used by edit/resend to update the edited message's content.

    **src-tauri/src/db/mod.rs** — Add three new DbCommand variants following the existing pattern (each carries a `reply: oneshot::Sender<anyhow::Result<()>>`):

    **start_chat command** per D-02:
    Signature: `pub async fn start_chat(db: State<'_, DbWorker>, cancel_state: State<'_, CancelState>, channel: Channel<StreamChunk>, conversation_id: String, content: String) -> Result<(), String>`

    Implementation steps:
    1. Cancel any existing stream: if cancel_state.token.lock().unwrap().is_some(), cancel it and clear it (prevents concurrent streams per RESEARCH Pitfall 4).
    2. Load conversation from DbWorker via `DbCommand::LoadConversations` then filter by ID (or add a dedicated LoadConversation variant — simpler to filter from LoadConversations).
    3. Load messages via `DbCommand::LoadMessages`.
    4. Load character via `DbCommand::LoadCharacters` then find by character_id from conversation.
    5. Load provider via `DbCommand::LoadProviders` then find by provider_id from conversation. If no provider configured, send `StreamChunk::Error { error: "No provider configured...", error_type: "no_provider_configured" }` and return Ok(()).
    6. Load API key via `tokio::task::spawn_blocking(move || KeyringStore::load_key(&provider.id))`. If provider requires key and key missing, send `StreamChunk::Error { error: "No API key...", error_type: "no_api_key" }` and return Ok(()). If Ollama (no key required), use empty string.
    7. Compute next sort_order: max sort_order from loaded messages + 1.
    8. Save user message via `DbCommand::SaveMessage` per D-04 (save immediately).
    9. Build system prompt from character personality + scenario per D-05: `format!("{}\n\n{}", character.personality, character.scenario)`. If both empty, use a minimal fallback like "You are a helpful assistant."
    10. Resolve GenerationParams from provider via `AiService::from_provider_config(&provider)`.
    11. Set up CancellationToken: create new token, store in CancelState.
    12. Spawn the stream loop via `tokio::spawn`: call `AiService::stream_chat` (or equivalent method from Plan 01) with channel, cancel_token, provider, system_prompt, messages (including the new user message), api_key, params.
    13. Return `Ok(())` — the spawned task continues sending StreamChunk events.

    **stop_generation command** per D-03:
    Signature: `pub async fn stop_generation(cancel_state: State<'_, CancelState>) -> Result<(), String>`
    Implementation: Take the CancellationToken from CancelState (lock, take, unlock), call `token.cancel()`. Return Ok(()). The spawned stream task will detect cancellation via tokio::select! and send a Complete with stop_reason "cancelled".

    **regenerate command** per D-11, D-13:
    Signature: `pub async fn regenerate(db: State<'_, DbWorker>, cancel_state: State<'_, CancelState>, channel: Channel<StreamChunk>, conversation_id: String) -> Result<(), String>`
    Implementation: Delete the last AI message from DB via DbCommand::DeleteMessage. Then re-invoke the streaming flow (steps 2-12 from start_chat, but WITHOUT saving a new user message — just stream with the existing conversation history minus the deleted AI message).

    **edit_and_resend command** per D-08, D-09:
    Signature: `pub async fn edit_and_resend(db: State<'_, DbWorker>, cancel_state: State<'_, CancelState>, channel: Channel<StreamChunk>, message_id: String, new_content: String) -> Result<(), String>`
    Implementation:
    1. Load the message by ID (need to query from loaded messages — add a helper or filter from LoadMessages).
    2. Update the message content via DbCommand::UpdateMessageContent.
    3. Delete all subsequent messages via DbCommand::DeleteMessagesAfterSortOrder with the message's sort_order.
    4. Re-invoke the streaming flow with the truncated history (same as regenerate, but with the edited message content).

    **commands/mod.rs:** Add `pub mod chat;`

    **lib.rs:** Add CancelState to managed state: `.manage(CancelState { token: std::sync::Mutex::new(None) })` before `.invoke_handler(...)`. Add all four commands to `invoke_handler`: `commands::chat::start_chat`, `commands::chat::stop_generation`, `commands::chat::regenerate`, `commands::chat::edit_and_resend`.

    NOTE: For loading individual entities (single message by ID, single conversation by ID), the simplest approach is to use the existing batch-load commands (LoadMessages, LoadConversations, LoadProviders, LoadCharacters) and filter in memory. This avoids adding new DbCommand variants for single-entity lookups, keeping the scope minimal.
