## Task 01-03-02: Verify F9 keyboard shortcut toggles sidebar

<read_first>

- persona/src/routes/+layout.svelte
- persona/src/lib/stores/app.svelte.ts
- persona/src/lib/components/layout/AppHeader.svelte
  </read_first>

<action>
With `bun tauri dev` running:

1. Press **F9** key while the app has focus
2. Verify the conversation sidebar collapses (width transitions from 288px to 0)
3. Press **F9** again
4. Verify the sidebar expands back

The F9 handler is already implemented in `src/routes/+layout.svelte`:

```javascript
const onkey = (e: KeyboardEvent) => {
    if (e.key === 'F9') {
        e.preventDefault();
        app.toggleSidebar();
    }
};
window.addEventListener('keydown', onkey);
```

This should work identically in the Tauri webview because the webview receives standard DOM keyboard events.

If F9 does not work:

- Verify the Tauri window has focus (click inside the webview first)
- Check for macOS system-level F9 conflicts (Mission Control may capture F9 on some macOS versions; if so, `fn+F9` may be needed)
- Verify `app.toggleSidebar()` is being called (add `console.log` temporarily)
  </action>

<acceptance_criteria>

- Pressing F9 toggles the conversation sidebar visibility
- Sidebar collapses on first F9 press
- Sidebar expands on second F9 press
- No JavaScript errors when pressing F9
  </acceptance_criteria>

## Task 01-03-03: Verify Enter/Ctrl+Enter send and Shift+Enter newline shortcuts

<read_first>

- persona/src/lib/components/chat/MessageInput.svelte
- persona/src/lib/stores/app.svelte.ts
  </read_first>

<action>
With `bun tauri dev` running and a conversation active:

1. Click on the message input textarea
2. Type some text
3. Press **Enter** → verify the message sends (text clears, message appears in chat)
4. Type some text
5. Press **Ctrl+Enter** (or **Cmd+Enter** on macOS) → verify the message sends
6. Type some text
7. Press **Shift+Enter** → verify a newline is inserted in the textarea (message does NOT send)
8. Verify the hint text "Enter to send · Shift+Enter for newline" is visible below the input

The keyboard handler is already implemented in `src/lib/components/chat/MessageInput.svelte`:

```javascript
function handleKey(e: KeyboardEvent) {
    if ((e.metaKey || e.ctrlKey) && e.key === 'Enter') {
        e.preventDefault();
        handleSubmit();
    }
    if (e.key === 'Enter' && !e.shiftKey && !e.metaKey && !e.ctrlKey) {
        e.preventDefault();
        handleSubmit();
    }
}
```

If Enter doesn't send:

- Verify the textarea has focus
- Check `handleKey` is bound to `onkeydown`
- Note: mock streaming will simulate a response (this is expected behavior in Phase 1)
  </action>

<acceptance_criteria>

- Pressing Enter in the message input sends the message
- Pressing Ctrl+Enter (or Cmd+Enter on macOS) sends the message
- Pressing Shift+Enter inserts a newline (does NOT send)
- Sent messages appear in the chat area
- Input textarea clears after sending
  </acceptance_criteria>

## Task 01-03-04: Verify AppHeader drag region moves the native window

<read_first>

- persona/src/lib/components/layout/AppHeader.svelte
- persona/src/app.css
  </read_first>

<action>
With `bun tauri dev` running:

1. Click and hold on the AppHeader area (the top bar with app title and nav tabs)
2. Drag the mouse → the native window should move with the cursor
3. Click and hold on an interactive element within the header (nav tab, sidebar toggle button)
4. Drag → the window should NOT move (these are `.no-drag` elements)

The CSS classes are already defined in `src/app.css`:

```css
.drag-region {
  -webkit-app-region: drag;
  app-region: drag;
}
.no-drag {
  -webkit-app-region: no-drag;
  app-region: no-drag;
}
```

These CSS properties are recognized by Tauri's webview (WKWebView on macOS, WebView2 on Windows, WebKitGTK on Linux) and delegate window dragging to the native window manager.

If dragging doesn't work:

- Verify AppHeader has the `drag-region` class applied
- Verify interactive elements within AppHeader have `no-drag` class
- On macOS, verify `window.json` capability includes `core:window:allow-start-dragging`
- Check that `-webkit-app-region: drag` is not being overridden by other CSS
  </action>

<acceptance_criteria>

- Dragging from the AppHeader area moves the native window
- Dragging from interactive elements (buttons, nav tabs) in the header does NOT move the window
- Window position changes when dragged from the header
  </acceptance_criteria>
