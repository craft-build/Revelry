# Phase 5 — UI Design Contract

> Visual and interaction contract for Context Engineering & Lorebook. Generated by gsd-ui-researcher.
> GTK4/libadwaita + Relm4 native desktop application. Design system inherited from Phase 1, extended by Phases 3 and 4.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | Adwaita (libadwaita v1.5+) |
| Preset | Adwaita default (system-managed light/dark) |
| Component library | GTK4 + libadwaita widgets |
| Icon library | relm4-icons 0.11.0 (bundled Adwaita symbolic icons) |
| Font | System font (Adwaita Sans / Inter variant on GNOME; system-ui on macOS/Windows) |
| CSS framework | GTK CSS via libadwaita stylesheet |

**Inheritance:** Spacing, typography, and color contracts are fully inherited from Phase 1 UI-SPEC (§Spacing Scale, §Typography, §Color). This document lists Phase 5 additions and exceptions only. Do not redefine base tokens.

---

## Spacing Scale

Inherited from Phase 1 (multiples of 4):

| Token | GTK Value | Usage |
|-------|-----------|-------|
| xs | 4 | Icon gaps, inline padding |
| sm | 8 | Compact element spacing |
| md | 12 | Default element spacing (Adwaita standard) |
| lg | 16 | Section padding, content margins within AdwClamp |
| xl | 24 | Section breaks, AdwPreferencesGroup spacing |
| 2xl | 32 | Page-level padding, sidebar/content margins |
| 3xl | 48 | Major section breaks, welcome/empty state spacing |

**Phase 5 Additions & Exceptions:**
- **Context utilization progress bar height:** 4px — thin, glanceable, not dominant (D-15 "thin progress bar"); 4px maintains grid alignment while still feeling slim
- **Progress bar margin:** 0px vertical — sits flush against the input area, visually part of the input bar boundary
- **Lorebook entry row minimum height:** 48px — compact rows for entry list, matching AdwActionRow density
- **Lorebook entry editor content area:** 120px minimum height for GtkTextView (entry content field)
- **Lorebook entry list row spacing:** 4px (xs) between rows — compact list feel
- **Token budget label gap:** 8px (sm) between the number entry and its label

## Typography

Inherited from Phase 1 — use Adwaita CSS style classes exclusively. No hard-coded sizes or weights.

| Role | Adwaita CSS Class | Approx. Size | Weight | Line Height | Phase 5 Usage |
|------|-------------------|-------------|--------|-------------|---------------|
| Body | `.body` | 14pt | 400 | 1.5 | Entry content preview, field labels |
| Heading | `.heading` | 16pt | 700 | 1.2 | Lorebook section titles, entry editor title |
| Caption | `.caption` | 12pt | 400 | 1.4 | Token counts, depth labels, keyword hints, utilization percentage |
| Caption Heading | `.caption-heading` | 12pt | 700 | 1.4 | Entry name in list rows |
| Title 4 | `.title-4` | 18pt | 700 | 1.2 | Lorebook page title |
| Dimmed | `.dimmed` / `.caption, .dimmed` | 12pt | 400 | 1.4 | Disabled entry names, deactivated state labels |

**Phase 5 Specific:**
- **Entry name in lorebook list:** `.caption-heading` class — compact but bold for scanability
- **Keyword list in entry row:** `.caption` class, comma-separated, max 1 line, ellipsize at word boundary
- **Token count in entry row:** `.caption` class, right-aligned suffix, format: `"{n} tokens"`
- **Context utilization percentage tooltip:** `.caption` class in tooltip — `"Using {used} / {total} tokens ({pct}%)"` — always visible as progress bar, percentage on hover
- **Depth number labels:** `.caption` class for all numeric fields (depth, scan depth, recursive depth)

**Accent reserved-for (Phase 5 extensions):**
- `suggested-action` buttons: "Add Entry", "Save Entry"
- Active/selected lorebook entry highlight
- Switch toggle in "on" state (AdwSwitchRow default)
- **Not for:** Context utilization indicator (uses semantic success/warning/destructive colors per D-15)

**Phase 5 Style Class Usage:**
- `.success` → context utilization progress bar fill when < 70%
- `.warning` → context utilization progress bar fill when 70–90%
- `.error` / `.destructive-action` → context utilization progress bar fill when > 90%
- `.error` → validation messages in lorebook editor
- `.dimmed` → disabled/deactivated lorebook entries in the list
- `.accent` → token budget labels at limit, activated entry count

### Context Utilization Color Logic (D-15)

| Utilization | Progress Bar Fill | CSS Variable | Visual Intensity |
|-------------|-------------------|--------------|------------------|
| 0–69% | Green | `--success-bg-color` | Low — everything is fine |
| 70–89% | Yellow/Amber | `--warning-bg-color` | Medium — budget pressure |
| 90–100% | Red | `--destructive-bg-color` | High — context full, truncation active |

The progress bar background (track) always uses `--card-bg-color` (subtle, receded). The fill uses the semantic color above. Colors transition at the boundaries — no animation, immediate switch.

## Visual Hierarchy & Focal Points

### Chat Screen (with conversation active)
**Focal point:** Context utilization progress bar — the colored fill (green/yellow/red) draws the eye at the boundary between message list and input area. It is the primary glanceable indicator for this phase's functionality.

**Secondary hierarchy:**
1. Input text area — where the user types (existing)
2. Send button — primary action (existing)
3. Context utilization tooltip (on hover) — detail layer

### Lorebook Page (Character Editor)
**Focal point:** Lorebook entry list rows — the primary content area. Entry names in `.caption-heading` draw attention first, followed by keyword previews and token counts.

**Secondary hierarchy:**
1. "Add Entry" button — primary action for empty state
2. Scan Depth / Recursive Depth spin rows — configuration, less prominent
3. Activation settings tip — contextual help, `.dimmed`

## Layout Specifications

### 1. Context Utilization Bar in InputBar

The context utilization bar is a thin `GtkProgressBar` placed at the **top** of the InputBar's vertical container, directly above the horizontal row containing the text view and send button. This places it at the boundary between the message list and the input area — the most glanceable position while typing (D-14).

```
InputBar (GtkBox, vertical):
┌──────────────────────────────────────────────────────┐
│ GtkProgressBar "context-utilization-bar"             │  ← 4px, flush top
│ ████████████░░░░░░░░░░░░░░░░░░░░░░░░░ (green < 70%) │
├──────────────────────────────────────────────────────┤
│ GtkBox (horizontal, spacing: 8)        ← existing    │
│ ┌────────────────────────────────────┐ [Send ▶]     │
│ │ GtkTextView (multi-line)           │               │
│ │ Ctrl+Enter to send                 │               │
│ └────────────────────────────────────┘               │
└──────────────────────────────────────────────────────┘
```

**Implementation details:**
- `GtkProgressBar` with `set_fraction(used_tokens / total_tokens)`
- Height: 4px (set via CSS: `min-height: 4px;`)
- No text overlay on the bar — it's too thin
- Show percentage + token counts on hover via `set_tooltip_text()`
- CSS class `context-utilization-bar` for custom styling
- Progress bar fill color changes based on utilization tier:
  - `< 70%`: Apply `.success` CSS class to the progress bar trough fill
  - `70–90%`: Apply `.warning` CSS class
  - `> 90%`: Apply `.error` CSS class
- The bar is always visible when a conversation is active; hidden when no conversation is loaded

**CSS for the progress bar:**

```css
context-utilization-bar {
  min-height: 4px;
}

context-utilization-bar trough {
  min-height: 4px;
  background-color: var(--card-bg-color);
}

context-utilization-bar.success progress {
  background-color: var(--success-bg-color);
}

context-utilization-bar.warning progress {
  background-color: var(--warning-bg-color);
}

context-utilization-bar.error progress {
  background-color: var(--destructive-bg-color);
}
```

**Update trigger (D-16):**
- Update the fraction and color class after every prompt assembly:
  - On message send (before streaming starts)
  - On stream complete (AI response added to history)
  - On persona change in chat header
  - On lorebook activation state change
- The ChatPanel computes the fraction from `AssembledPrompt` metadata and sends `InputBarMsg::UpdateContextUtilization { used, total }`

**Tooltip:**
- Normal: `"Using {used} / {total} tokens ({pct}%)"`
- When truncation occurred (history was trimmed): `"Using {used} / {total} tokens ({pct}%) — History truncated to fit context"`
- Tooltip provides the detail that the bar itself cannot show at 4px height

## Interaction Specifications

### Context Utilization Update Flow

1. User sends message / AI response completes / persona changes
2. PromptEngine::assemble() is called with all layers (system + char + lorebooks + persona + history)
3. Token count is computed from the assembled prompt
4. ChatPanel receives `AssembledPrompt` metadata with `used_tokens` and `total_tokens`
5. ChatPanel sends `InputBarMsg::UpdateContextUtilization { used, total }` to InputBar
6. InputBar computes fraction and determines color tier
7. GtkProgressBar updates fraction and CSS class (`.success` / `.warning` / `.error`)
8. Tooltip text updates with current token numbers

### Lorebook Entry Add Flow

1. User clicks "Add Entry" button on Lorebook page
2. `AdwPreferencesWindow` opens with title "New Entry"
3. All fields start at defaults: empty name, empty keywords, empty content, depth=4, budget=0, enabled=true
4. User fills in fields
5. User clicks "Save Entry" (`.suggested-action`)
6. Validation: name required, keywords required, content required
7. **On valid:** dispatch `SaveLorebookEntry(entry)` → DbService; close editor; toast "Entry added"
8. **On invalid:** show `.error` label below the failing field; do not close editor

### Lorebook Entry Edit Flow

1. User clicks "Edit" button on an entry row
2. `AdwPreferencesWindow` opens with title "Edit Entry", fields pre-populated from entry data
3. User modifies fields
4. User clicks "Save Entry"
5. Validation same as add flow
6. **On valid:** dispatch `SaveLorebookEntry(entry)` → DbService; close editor; toast "Entry updated"
7. **On cancel with changes:** `AdwMessageDialog` "Discard changes?" → [Keep Editing] [Discard]

### Lorebook Entry Delete Flow

1. User clicks "Delete" on an entry row (hover reveals `.destructive-action` style)
2. `AdwMessageDialog` appears:
   - Title: "Delete Entry?"
   - Body: "This will permanently delete '{name}' and remove it from the AI context. This cannot be undone."
   - Buttons: [Don't Delete] [Delete] (`.destructive-action`)
3. **On confirm:** dispatch `DeleteLorebookEntry(id)` → DbService
4. On `LorebookEntryDeleted`: remove row from list, toast "Entry deleted"

### Lorebook Entry Enable/Disable Toggle

1. User clicks the enabled/disabled icon on an entry row, or toggles the "Enabled" AdwSwitchRow in the entry editor
2. Entry's `enabled` field is updated
3. Entry row's visual state updates (`.dimmed` when disabled)
4. No toast — this is a silent state change, consistent with D-07 (indicator-only for context changes)
5. Entry is saved to database immediately (no confirmation needed for toggle)

## Phase 5 Specific Notes

### Context Utilization Bar — Not a Loading Indicator

The context utilization bar is a **gauge**, not a progress indicator. It shows "how full is the bucket," not "how long until done." It uses `GtkProgressBar` for its visual appearance (colored fill fraction) but is semantically different from a loading spinner. The bar should never animate or pulse — it's a static snapshot that updates discretely.

### Lorebook Page Positioning — After Scenario, Before Advanced

The Lorebook page is inserted as page 4 (after Scenario, before Advanced) in the CharacterEditor. This places world-building content logically after the character's conversational setup (scenario, first message) and before technical settings (system prompt, post-history instructions). Users editing a character's world info won't need to scroll past advanced settings to reach it.

### Depth-from-Bottom Semantics (D-11)

The "Depth" field in the lorebook entry editor follows SillyTavern's depth-from-bottom convention:
- Depth 0 = inject after the very last message
- Depth 4 = inject 4 messages from the end (between the 4th-from-last and 5th-from-last messages)

The UI clearly labels this with a subtitle and tip to prevent confusion (users might expect "depth" to mean "distance from top"). The tip text "Depth 0 injects at the very end. Depth 4 injects 4 messages from the end." is unambiguous.

### No Context Breakdown Popover (Deferred)

Per the 05-CONTEXT.md deferred items, a detailed per-layer token breakdown popover is deferred to future polish. The context utilization bar shows only the aggregate fraction. The tooltip provides total used/total tokens. Users who need per-layer detail can consult the debug log output (tracing).

### Lorebook Import/Export — character_book JSON Compatibility

The `character_book` JSON column on the `characters` table is preserved for import/export compatibility with SillyTavern's CharacterCardV2 spec. When importing, entries in the `character_book` JSON are parsed into the `lorebook_entries` table. When exporting, entries from the table are serialized back into the `character_book` JSON field. The UI does not expose the raw JSON column — all editing happens through the structured lorebook entries.

### Persona Compression — No Dedicated UI

Persona compression (D-06: full → trimmed → minimal → essential) is a backend-only behavior that happens during prompt assembly when token budget is tight. There is no UI control or indicator for which compression tier is active. The context utilization bar indirectly shows when compression may be occurring (when utilization is high), but the user never sees "Persona compressed to minimal" explicitly. This matches D-07's silent indicator approach.

### AdwSpinRow Usage

`AdwSpinRow` (available in libadwaita v1.5+) is used for all numeric fields: depth, token budget, scan depth, and recursive depth. It provides a labeled row with inline +/- controls, matching the Adwaita preferences pattern established in Phase 1 and Phase 4. AdwSpinRow is preferred over a bare GtkSpinButton because it integrates with the PreferencesGroup layout.
